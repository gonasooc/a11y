## 1. 이번에 바꿔 보는 질문

**접근 가능한 화면을 만났더라도, 하려던 일을 끝내지 못할 수 있다.** 입력 중 시간이 끝나고, 상담으로 넘어가면서 처음부터 설명해야 하고, 쉬운 안내가 원문보다 늦게 수정되는 상황을 생각해 볼 수 있다. 앞의 두 문서가 찾은 장벽을 출발점으로, 이번에는 그 장벽이 생기는 서비스의 처리 과정과 운영 업무를 바꾸는 도구를 제안한다.

06·07은 이미 읽기·조작 우회, 쉬운 말, 교육, 당사자 평가, 자동 관측, 인증 관문, 법제·공공데이터 기반을 다뤘다. 여기에 검사기나 설명기를 하나 더 얹기보다 **중단 뒤 복구, 상담 인계, 콘텐츠 갱신, 이용 방식 전달, 구매 검수, 수정안 선택**이라는 여섯 작업을 잡는다.

## 4. 아이디어 23. 중간부터 다시: 신청·예약 이어하기

**무엇**: 서비스를 운영하는 쪽에 붙이는 저장·복구 도구다. 이용자가 쉬었다 돌아오거나 오류를 수정할 때, 확인된 입력과 진행 단계를 복원한다. 첫 적용 대상은 복지관 프로그램 신청이나 일반 예약처럼 범위를 좁힐 수 있는 과업이다.

**근거와 가설**

- [01 §7.3·§7.4](01-digital-access-environment.md)는 조작 시간과 복잡한 절차가 이용을 막은 사례를 담고 있다. 이 사례가 세션 만료에 따른 데이터 손실을 직접 입증하는 것은 아니다. ‘반복 입력과 재시작이 추가 장벽일 수 있다’는 제품 가설로 연결한다.
- W3C의 인지 접근성 보충 지침은 작업 중 저장, 시간 종료에 따른 손실 방지, 다시 로그인한 뒤 작업을 유지하는 방식을 제안한다. WCAG 준수를 위한 필수 조항과는 구분되는 설계 자료다. [B, W3C §4.5.9](https://www.w3.org/TR/coga-usable/)
- WCAG 2.2의 중복 입력 기준은 같은 과정에서 이미 입력한 정보를 다시 쓰게 하는 문제를 다루지만, 세션 사이의 저장까지 요구하지는 않는다. 세션을 넘는 이어하기는 여기서 제안하는 제품 범위다. [B, 중복 입력 해설](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)

**사용 흐름**

1. 시작할 때 저장되는 항목, 보관 기간, 재개 방법을 알려 준다. 저장하지 않는 선택도 제공한다.
2. 단계마다 ‘어디까지 저장됐는지’를 글자와 보조기술로 확인할 수 있게 한다. 연결이 끊기면 저장 완료라고 표시하지 않는다.
3. 다시 접속하면 필요한 인증을 거친 뒤 ‘완료한 것·남은 것·달라진 조건’을 보여 준다. 초점도 재개 지점을 찾기 쉬운 위치로 옮긴다.
4. 재고·일정·가격·신청 자격처럼 바뀔 수 있는 조건은 다시 확인한다. 제출 여부가 불명확하면 기존 접수 상태부터 확인해 중복 신청을 막는다.

**첫 버전과 검증**

- 모형 신청서 하나에 저장, 재접속, 오류 후 복귀, 접수 확인을 구현한다. 처음에는 가상 개인정보를 쓴다.
- 시험 상황은 자리 비움, 연결 끊김, 제출 결과를 받기 전 중단의 세 가지다. 기존 방식과 개선 방식에서 재입력 항목 수, 잘못 복원된 값, 중복 접수, 원하는 신청의 완료 여부를 기록한다.
- 화면낭독·확대·키보드 등 해당 과업의 이용 방식으로 실제 조작하게 한다. ‘저장 기능이 있다’와 ‘저장·복구 상태를 알 수 있다’를 따로 확인한다.
- **중단 조건**: 운영기관이 초안 보관이나 접수 상태 확인을 지원하지 않으면 범용 확장으로 해결한다고 약속하지 않는다. 한 기관 전용 구현이나 설계 패턴으로 범위를 줄인다.

**운영·비용 가설**: 신청 담당 기관이 통합·유지 비용을 내고, 이용자는 추가 비용 없이 쓴다. 재신청·문의 대응 부담이 실제로 줄어드는지 확인해야 한다. 모형은 1~2주를 가정하지만, 운영 시스템 연동 일정은 별도다.

**가장 큰 함정**: 입력 내용 보존과 인증 세션 연장을 혼동하는 것이다. 비밀번호·인증번호·결제 승인 정보를 복구 대상으로 삼지 않는다. 초안 접근 권한, 공용 기기 노출, 삭제·만료를 함께 설계해야 한다. 저장이 예약·가격의 보장을 뜻하지 않는다는 점도 분명히 한다.

## 5. 아이디어 24. 문자로 끝내기: 같은 조건의 상담 인계

**무엇**: 이용 중 막힌 일을 문자 상담으로 넘겨 담당자가 끝까지 처리할 수 있게 하는 운영 도구다. 사용자가 고른 실패 지점·요청·필요한 정보만 전달하고, 담당자가 바뀌어도 처리 상태를 이어받는다. 문자부터 검증하되, 선호에 따라 음성·수어 상담으로 이어지는 경로도 설계한다.

**근거와 가설**

- [01 §7.1·§7.2](01-digital-access-environment.md)에는 문의 경로의 부재와 음성통화에 의존하는 절차가 기록돼 있다. [01 §7.3](01-digital-access-environment.md)은 다른 채널을 쓰면 비용이 늘어나는 사례도 전한다. 모든 업종의 현재 상황을 뜻하지는 않는다.
- [02 §5.2](02-private-sector-legal-obligations.md)가 다룬 대기 시간과 자기결정권을 상담 품질 지표로 가져온다. 상담창의 존재보다 실제로 어떤 업무를 끝낼 수 있는지 확인한다.
- W3C는 사람이 돕는 경로를 쉽게 찾고 선호하는 방식으로 이용하게 하며, 도움을 받기 위해 복잡한 메뉴나 긴 양식을 통과하게 하지 말 것을 제안한다. [B, 사람의 도움 제공](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o7p01-human-help/)

**사용 흐름**

1. 예약 변경 화면에서 ‘문자로 이어서 해결’을 고른다. 어떤 정보가 상담원에게 가는지 확인한다.
2. 상담원은 이용자가 원한 변경, 실패한 단계, 이미 확인된 내용을 받는다. 필요한 경우 추가 확인을 요청한다.
3. 상담팀이 처리 권한을 가진 업무와 추가 담당자가 필요한 업무를 구분한다. 다른 담당자로 넘겨도 사용자가 설명을 처음부터 반복하지 않게 한다.
4. 완료 후 변경 결과를 이용자가 확인한다. ‘상담 종료’, ‘업무 처리 완료’, ‘이용자 결과 확인’을 별도 상태로 둔다.

**차별점은 상담 권한과 조건이다.** 온라인에서 제공하던 가격·혜택·신청 기회를 대체 경로에서도 유지할 수 있는지 기관과 먼저 합의한다. 동등한 조건을 보장하지 못하는 항목은 실제 차이를 보여 준다. 이것은 제품의 운영 목표이며, 개별 사안의 법적 판단을 자동화한다는 뜻이 아니다.

**첫 버전과 검증**

- 협력 기관 한 곳의 예약 변경 업무만 다룬다. 기존 문자 상담 수단과 수동 인계표로도 시작할 수 있다.
- 가상 문의 10건으로 업무 담당자 도달, 설명 반복, 대기 시간, 전화 전환 요구, 최종 변경 성공을 확인한다. 이후 당사자와 실제 이용 흐름을 검증한다.
- **중단 조건**: 문자 상담원에게 처리 권한이 없고 매번 전화로 돌아가야 한다면, 챗봇이나 화면 개발보다 내부 업무 규칙 변경이 먼저다.

**운영·비용 가설**: 기관이 상담 운영비와 인계 도구 비용을 낸다. 반복 문의 감소가 도입 이유가 될 수 있지만 아직 검증하지 않았다. 첫 버전에는 응대 가능한 시간과 인력이 포함돼야 한다.

**가장 큰 함정**: 문자만 제공하면 모든 농인이 이용할 수 있다고 가정하는 것이다. 문자·수어·쉬운 설명의 필요는 사람마다 다르다. 도움은 선택할 수 있게 하고, 스스로 이용하는 경로의 개선도 계속한다. 인증이 필요한 업무는 기관이 승인한 접근 가능한 확인 수단을 사용한다.

## 6. 아이디어 25. 한 번 쓰고 함께 발행: 접근 가능한 원본 편집실

**무엇**: 행사·상품·신청 안내의 핵심 내용을 구조화해 한 번 작성하고, 그 원본에서 이미지 홍보물과 접근 가능한 웹 안내, 쉬운 안내를 함께 관리하는 편집 도구다. 핵심 기능은 **원문이 바뀌었을 때 영향을 받는 안내를 찾아 다시 확인하고 함께 발행하는 것**이다.

**근거와 가설**

- [01 §4.4·§7.4](01-digital-access-environment.md)는 이미지에 갇힌 상품정보와 쉬운 정보의 부족을 다룬다. [02 §11](02-private-sector-legal-obligations.md)은 서비스를 만드는 쪽의 과제를 정리한다.
- 06의 아이디어 1·4·12는 이미 만들어진 정보에서 텍스트나 설명을 얻는 데 유용하다. 이번에는 처음 작성할 때부터 접근 가능한 원본을 함께 만드는 흐름을 시험한다.
- ‘쉬운 안내가 정정에서 빠지는 일이 잦다’는 발생률 자료는 기존 문서에 없다. 아래 편집·정정 흐름의 수요는 별도로 확인해야 한다.

**사용 흐름**

1. 담당자가 대상, 해야 할 일, 비용, 기한, 장소, 예외, 문의 방법을 입력한다. 사진·도식에는 별도의 설명을 붙인다.
2. 같은 사실 필드로 일반 웹 안내와 이미지 시안을 만든다. 쉬운 안내는 초안과 검수 상태를 분리하고 당사자 검수자가 확인한다.
3. 마감일을 바꾸면 그 값을 쓰는 모든 산출물과 검수 상태가 나타난다. 검수가 필요한 쉬운 설명은 재검토로 돌린다.
4. 담당자가 확인한 묶음을 발행하고 이전 버전·정정 내역을 남긴다. 출력·복사돼 통제 밖으로 나간 홍보물은 교체 대상 목록으로 관리한다.

**첫 버전과 검증**

- 복지관이나 소규모 기관의 프로그램 안내 5개를 대상으로 일반 웹 안내와 쉬운 안내 두 형식만 지원한다. 이미지 시안은 다음 단계로 미뤄도 된다.
- 날짜 변경, 비용 변경, 신청 조건 추가를 넣어 누락된 형식과 잘못 남은 사실을 찾는다. 숫자·기한 일치 검사와 쉬운 설명의 의미 검수를 분리한다.
- 이용자에게 읽은 내용을 시험하듯 평가하기보다, 안내를 보며 신청 방법·기한·예외를 찾을 수 있는지 관찰한다. 어려움은 콘텐츠 수정의 근거로 쓴다.
- **중단 조건**: 담당자가 원본을 유지할 수 없거나 주 게시 채널이 텍스트·연결 링크를 허용하지 않으면, 해당 채널까지 자동 동기화된다고 표현하지 않는다.

**운영·비용 가설**: 콘텐츠 발행 기관이 편집·검수 비용을 낸다. AI 초안 생성비보다 원문 확인과 당사자 검수 시간을 먼저 예산에 넣는다. 소규모 편집 흐름은 2~3주 실험을 가정한다.

**가장 큰 함정**: 여러 형식을 만들었다는 사실만으로 내용의 동등성을 보장하는 것이다. 같은 숫자를 쓰더라도 예외가 빠지면 의미가 달라진다. 자동 생성은 초안으로 취급하고, 긴 이미지 하나에 모든 내용을 담은 대체 텍스트를 붙이는 방식에 머물지 않는다.

## 7. 아이디어 26. 내 이용 방식 카드: 원하는 지원을 골라 전달

**무엇**: 이용자가 ‘문자로 연락받기’, ‘한 번에 한 단계 보기’, ‘시간을 더 받고 싶음’ 같은 요청을 골라 서비스에 전달하고, 서비스가 적용한 것과 지원하지 못한 것을 회신하는 카드다. 첫 범위는 한 기관 안의 신청·상담 두 업무로 제한한다.

**근거와 가설**

- [01 §5·§7](01-digital-access-environment.md)은 확대, 화면낭독, 의사소통, 이해 지원 등 서로 다른 이용 방식을 보여 준다. 같은 장애유형 안에서도 필요한 지원을 하나로 정할 수 없다.
- W3C는 익숙한 화면과 사용자가 조정할 수 있는 표현 방식을 지원하도록 제안한다. 다만 이 자료가 기관 간 설정 전송 규격이나 이 카드의 효과를 검증한 것은 아니다. [B, 개인화와 익숙한 인터페이스](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o8p04-interface/)
- 서비스마다 같은 요구를 설명하는 부담의 크기는 아직 모른다. 따라서 **여섯 후보 가운데 탐색 우선의 아이디어**로 둔다.

**사용 흐름**

1. 카드에는 진단명이나 장애등급 대신 이용자가 원하는 동작을 적는다. OS의 보조기술 사용 여부를 몰래 탐지하지 않는다.
2. 사용자가 이번 기관에 보낼 항목과 적용 기간을 고른다. 기관 간 공유는 자동으로 하지 않는다.
3. 기관은 ‘문자 연락 적용’, ‘단계별 보기 적용’, ‘시간 조정은 담당자 확인 필요’처럼 결과를 돌려준다.
4. 사용자는 적용 전후를 확인하고 요청을 바꾸거나 해제할 수 있다. 카드를 쓰지 않아도 기본 서비스를 이용할 수 있어야 한다.

**첫 버전과 검증**

- 앱부터 만들지 않는다. 종이·접근 가능한 웹 양식으로 5개 안팎의 요청 항목을 정하고, 담당자가 실제로 처리할 수 있는지 본다.
- 당사자 5명과 신청→상담 전환을 시험해 반복 설명 횟수, 잘못 적용한 설정, 불필요하게 공개한 정보, 직접 설정하는 방식에 대한 선호를 기록한다.
- **중단 조건**: 두 업무 사이에서도 적용할 수 있는 요청이 거의 없거나, 설명 부담이 줄지 않으면 독립 제품을 접고 24번의 상담 선호 기능으로 합친다.

**운영·비용 가설**: 기관이 자기 서비스의 설정·상담 연동을 부담한다. 여러 기관이 참여하는 공통 규격은 단일 기관 실험 뒤의 과제다. 범용 호환성을 먼저 약속하지 않는다.

**가장 큰 함정**: 편의를 요청하는 과정이 새로운 등록·증명 절차가 되는 것이다. 필요한 지원만 최소한으로 전달하고, 요청만으로도 장애 관련 사정이 드러날 수 있음을 고려한다. 지원 프로필을 광고·고객 등급·가격 차등에 이용하는 구조는 만들지 않는다.

## 8. 아이디어 27. 사기 전에 써 보기: 접근성 구매·납품 검수팩

**무엇**: 키오스크·예약 솔루션·외부 입력 모듈 등을 구매하는 쪽이 요구사항과 납품 시험을 연결하도록 돕는 도구다. 제품 설명, 실제 납품 버전, 사용할 장소, 완료해야 할 과업, 미해결 문제의 담당자를 한 건으로 묶는다.

**근거와 가설**

- [01 §6.3](01-digital-access-environment.md)은 기기가 있어도 키패드·음성안내·호출벨이 제대로 작동하지 않은 현장 사례를 담고 있다. [04 §5](04-sources-and-verification.md)는 검증 모델 수, 판매 수, 설치 등록 수를 구분한다. 구매 서류와 사용 가능한 상태는 각각 확인해야 한다.
- 미국 GSA의 구매 안내는 요구사항 정의, 공급자 자료 요청, 제안 평가, 납품 검증을 연결하며 변경 버전의 재시험도 다룬다. 이 운영 흐름을 참고한다. 미국 조달 규칙을 한국 사업자의 법적 의무로 옮겨 적는 것은 아니다. [B, GSA 접근 가능한 제품 구매](https://www.section508.gov/buy/)

**사용 흐름**

1. 구매자가 ‘키보드만으로 예약 수정’, ‘음성안내로 상품 선택과 취소’처럼 실제로 필요한 과업을 정한다.
2. 공급자가 제품·버전·시험 환경·알려진 제한·수정 계획을 제출한다. 공급자의 주장과 구매자가 확인한 결과를 별도 칸에 둔다.
3. 계약 전 시연과 설치 후 검수를 구분한다. 현장에서는 접근 공간, 연결 장치, 소음, 직원 대응 등 실제 조건도 확인한다.
4. 실패 항목에는 담당자·조치 기한·재시험 방법을 붙인다. 수정 완료 통보 뒤 다시 시험하고, 업데이트나 계약 갱신 때 확인할 과업을 남긴다.

**첫 버전과 검증**

- 새 검사 엔진을 만들기 전에 요구사항 문서, 증빙 목록, 과업 시험표, 미해결 항목표부터 만든다.
- 구매 예정인 기관 한 곳에서 제품 하나를 골라 공급자 설명과 실제 시연을 대조한다. 구매 전에 발견한 사용 불가 과업과 공급자가 답하지 못한 조건을 기록한다.
- **중단 조건**: 구매 담당자에게 시험 결과를 계약·인수 결정에 반영할 권한이 없다면, 구매 도구로서의 가치는 제한된다. 그 조직의 승인 절차부터 확인한다.

**운영·비용 가설**: 구매 기관이 검수·조정 비용을 낸다. 첫 문서 묶음은 1주를 가정하되 실제 조달 기간은 훨씬 길 수 있다. 공급자에게 돈을 받고 좋은 평가를 제공하는 구조는 피한다.

**가장 큰 함정**: 체크리스트 완료를 새로운 인증마크처럼 판매하는 것이다. 산출물은 정해진 환경·과업의 검수 기록이다. 법적 준수 판정이나 모든 이용자에 대한 사용 보장이 아니다. 계약 문구가 필요한 경우에는 해당 기관의 계약 검토 절차로 넘긴다.

## 9. 아이디어 28. 고쳐서 다시 해 보기: 유급 당사자 완주 실험실

**무엇**: 제품팀이 해결할 실패 한 가지와 수정 후보를 가져오면, 당사자와 함께 시험해 어떤 수정을 채택할지 정하는 서비스다. 여기서 ‘완주’는 원하는 결과를 확인한 상태이며, 사용자가 원치 않는 신청을 취소하는 것도 과업에 따라 올바른 결과가 된다. 과업별 목표 상태를 미리 정의하고, 의도한 취소와 장벽 때문에 포기한 경우를 구분한다. 수행 중 목표 변경은 이유와 함께 별도로 기록한다.

**근거와 가설**

- [01 §7.6](01-digital-access-environment.md)의 사용성 개선 사례는 체크리스트만으로 알기 어려운 실제 조작 문제를 보여 준다. [06 §10.1](06-tool-ideas.md)은 당사자 참여와 보수를 원칙으로 둔다.
- 해외에는 당사자를 모집·훈련·연결하고 보수를 지급하는 접근성 조사 서비스 Fable이 이미 있다. 따라서 ‘당사자 테스트 플랫폼’ 자체를 새 시장으로 주장할 수는 없다. [C, Fable의 자체 서비스 설명](https://makeitfable.com/testers/)
- 한국어 과업, 국내 서비스의 운영 제약, 한 번의 수정과 재시험까지 묶은 작은 구매 단위가 채택될지는 별도 검증이 필요하다.

**사용 흐름**

1. 제품팀이 고칠 권한이 있는 과업 하나를 고른다. 예: ‘예약 날짜를 바꾸고 결과를 확인한다’.
2. 해당 이용 방식의 참여자를 모집하고 보수·소요 시간·정보 이용 범위를 먼저 정한다. 참여자에게 결함 발견이나 성공을 보수 조건으로 걸지 않는다.
3. 기존 방식과 수정안을 비슷한 난도의 과업으로 비교한다. 순서를 나누고 학습 효과·도움 개입을 기록한다.
4. 실패 장면, 수정 결정, 재시험 결과를 한 묶음으로 전달한다. 결과가 좋지 않으면 수정안 보류도 정상적인 산출물이다.

**첫 버전과 검증**

- 플랫폼을 만들기 전에 기관 1곳·과업 1개·당사자 6~8명으로 운영한다. 모든 장애유형을 대표한다고 표현하지 않는다.
- 보고서는 전체 평균 하나보다 이용 방식별 막힌 단계, 완료 여부, 오류 후 복구, 원치 않은 도움, 결과 이해를 보여 준다.
- 기관이 보고서를 받은 뒤 실제 수정 또는 배포 보류 결정을 했는지 확인한다. 좋은 의견을 들었다는 만족도만으로 제품 가치를 평가하지 않는다.
- **중단 조건**: 구매자가 수정 권한·시간·예산 없이 홍보용 참여만 원한다면 ‘수정과 재검증’ 서비스로 성립하지 않는다.

**운영·비용 가설**: 제품팀이 모집·진행·참여자 보수·재시험 비용을 낸다. 과업당 고정 범위로 시작하고, 좋은 결과가 나와야 대금을 받는 구조는 피한다. 모집과 접근 가능한 시험 준비가 끝난 뒤 2주 실험을 가정한다.

**가장 큰 함정**: 익숙한 고숙련 참여자 몇 명의 결과를 전체 이용자에게 확대하는 것이다. 고령자·초보자·발달장애인 등은 별도 모집 경로와 진행 방식이 필요할 수 있다. 참여자가 원하는 지원을 허용하고 기록하되, 원치 않은 타인 의존과 구분한다.

## 10. 무엇부터 만들 것인가

아래는 시장 조사 결과가 아닌 실행 순서 제안이다. 개발 시간보다 **누가 실제 운영을 바꿀 권한을 갖고 있는가**를 먼저 본다.

| 확보한 조건 | 첫 선택 | 첫 산출물 | 아직 만들지 않아도 되는 것 |
|---|---|---|---|
| 신청·예약 서비스를 바꿀 협력 기관이 있다 | **23 + 28** | 중단 후 이어하기 모형과 당사자 비교 결과 | 범용 확장, 여러 서비스 통합 플랫폼 |
| 업무 처리 권한이 있는 문자 상담팀이 있다 | **24**, 필요하면 26 일부 | 예약 변경 한 업무의 인계·완료 기록 | 새 메신저, 범용 상담 AI |
| 안내문을 반복 제작하는 기관이 있다 | **25** | 원본·쉬운 안내의 정정과 재검수 흐름 | 모든 문서 형식을 지원하는 변환기 |
| 실제 구매·갱신 예정인 기관이 있다 | **27** | 과업 요구사항과 납품 검수표 | 공급자 순위 사이트 |
| 당사자와 제품팀을 연결할 수 있다 | **28** | 수정 결정까지 이어지는 유급 실험 한 건 | 참여자 마켓플레이스 |
| 아직 협력 기관이 없다 | 문제 인터뷰와 모형 준비 | 반복되는 실패 한 가지와 도입 조건 | 운영 연동이 이미 가능한 것처럼 보이는 제품 |

**기본 조합은 ‘23을 만들고 28로 확인’이다.** 23은 비교할 변화가 구체적이고, 28은 만든 기능이 실제로 도움이 되는지 알아보는 방법이다. 다만 인터뷰에서 재시작 문제가 드물거나 기존 저장 기능으로 충분하다고 확인되면 23을 고집하지 않는다.

26은 서비스별 지원 가능 항목이 확인되기 전까지 독립 제품 우선순위를 낮춘다. 25는 편집자가 원본을 계속 관리할 동기가 있어야 하고, 27은 실제 구매 일정이 있어야 검증할 수 있다. 이 조건을 확인하는 것이 기능을 늘리는 것보다 앞선다.

## 11. 첫 실험: 신청을 중단해도 이어서 끝낼 수 있는가

**이 실험은 실행 계획이며 아직 수행하지 않았다.** 기관 협의·참여자 모집·보수 합의가 끝난 뒤 2주를 가정한다. 모집과 연동 준비 기간은 별도로 잡는다.

| 단계 | 할 일 | 남길 결과 |
|---|---|---|
| 시작 전 | 과업 하나, 대상 이용 방식, 가상 데이터, 완료 상태, 도움 허용 범위, 중단 조건을 정한다 | 결과를 보기 전에 작성한 실험 계획 |
| 1주차 앞부분 | 기존 과정에서 어디서 중단되고 무엇을 잃는지 관찰한다 | 실패 지점과 입력·접수 상태의 구분 |
| 1주차 뒷부분 | 저장·재개·접수 확인 모형을 만든다. 잘못된 초안 연결 등 기본 결함을 먼저 점검한다 | 비교 가능한 기존안·수정안 |
| 2주차 앞부분 | 6~8명이 비슷한 난도의 과업을 수행한다. 기존안과 수정안의 순서를 나눈다 | 이용 방식별 관찰, 반복 입력, 오류·도움 기록 |
| 2주차 뒷부분 | 잘못 복원된 정보, 중복 제출, 복구 후 혼란을 먼저 검토하고 다음 범위를 정한다 | 진행·수정·보류 결정과 이유 |

### 11.1 완료율 하나로 평가하지 않는다

| 지표 | 정의·기록 방식 |
|---|---|
| 원하는 과업 완료 | 미리 정한 목표 상태가 확인된 과업 수 / 시도를 시작한 과업 수. 의도한 취소·장벽으로 인한 포기·실패·판정 불가를 구분한다 |
| 작업 손실 | 처음부터 다시 입력한 항목 수와 다시 수행한 단계 수 |
| 복구 오류 | 틀린 값 복원, 다른 초안 연결, 중복 접수, 바뀐 조건을 놓친 사례 |
| 시간 | 조작 시간·대기 시간·사용자가 선택한 휴식 시간을 구분한다 |
| 도움 | 스스로 완료, 원해서 받은 지원, 막혀서 불가피하게 받은 지원을 구분한다 |
| 결과 이해 | 저장·접수·완료·취소 중 현재 어떤 상태인지 이용자가 확인할 수 있는지 본다 |
| 운영 부담 | 기관의 연동·문의 처리·수정·검수에 든 시간을 기록한다 |

과업 안내를 받고 시도를 시작한 건을 분모로 삼으며, 첫 조작 전 접근 실패도 포함한다. 배정·시작·중단 수를 함께 적는다. 안전상 실험 중단으로 시도하지 못한 과업은 미실시로 별도 기록한다.

다른 사람의 정보가 보이거나 중복 접수가 생기는 결함은 실험 중단·수정 사유다. 반대로 작은 시험에서 그런 일이 없었다고 안전성이 입증됐다고 쓰지는 않는다. 잘못된 결과를 빨리 내는 방식이 좋은 완료율로 보이지 않도록 오류와 시간도 함께 읽는다.

### 11.2 05 문서와 연결하되, 인과효과를 과장하지 않는다

- 결과를 보기 전에 주요 질문과 지표를 정한다. 이미 본 데이터와 그 뒤 추가한 가설은 구분한다.
- 한 사람이 여러 과업을 한 횟수와 독립된 참여자 수를 함께 적는다. 반복 측정이나 항목 추가가 독립 표본을 늘리는 것은 아니다.
- 작은 실험의 결론은 ‘이 조건에서 어떤 실패가 줄었는가’다. 모집 경로와 이용 방식이 다른 집단에 대한 효과는 남은 질문이다.
- 정책 분석에 제공하려면 기관별 도입·실제 사용 시점, 과업과 측정 정의, 버전, 다른 동시 변경을 남긴다. 참여한 기관만 좋아졌다는 사실로 정책 효과를 주장하지 않는다.
- 개인정보와 업무 내용을 제외한 실험 설계·실패 유형·집계 지표부터 공개할 수 있다. 원자료 공개는 별도 동의와 재식별 가능성 검토가 필요하다.

## 12. 설계 원칙과 남아 있는 질문

### 12.1 앞 문서의 원칙을 이번 범위에 적용하기

06은 사용자 측 우회 도구의 원칙으로 ‘기업에 준수 수단으로 팔지 않는다’를 제시했다. 이번 문서는 **기업·기관이 자기 서비스와 운영을 고치는 도구**까지 범위를 넓힌다. 도입·검수·운영에 비용을 받는 모델을 검토하되, 자동 법적 준수나 인증 대체를 상품으로 약속하지 않는다.

1. **개선 부담은 공급자에게도 둔다.** 이용자가 장벽을 만날 때마다 새 앱을 설치하거나 장애를 증명하게 만들지 않는다.
2. **도움은 이용자가 선택한다.** 당사자의 결정을 대신하지 않고, 독립 이용과 원하는 지원 모두를 가능하게 한다.
3. **필요한 정보만 넘긴다.** 초안·상담·이용 방식 카드의 저장과 공유 범위를 분명히 하고 삭제·만료를 설계한다.
4. **상태를 구별한다.** 저장과 제출, 접수와 해결, 공급자의 수정 통보와 실제 재검증을 같은 것으로 표시하지 않는다.
5. **같은 정보를 유지한다.** 일반 안내와 접근 가능한 안내 사이에 금액·기한·예외·정정 사항이 어긋나지 않게 관리한다.
6. **기본 접근성을 갖춘 시험 도구를 제공한다.** 모집 양식, 동의 안내, 시험 화면, 결과 확인, 보수 수령 절차까지 이용할 수 있어야 한다.
7. **효과와 운영비를 함께 본다.** 이용자 부담이 줄어도 운영기관이 유지할 수 없으면 계속 쓰이지 않는다.

### 12.2 아직 모르는 것

- 당사자에게 반복 입력·재시작·상담 인계가 얼마나 자주 생기며, 기존 기능으로 해결되지 않는 부분이 무엇인가.
- 신청·예약 기관이 초안 저장과 접수 상태 확인을 실제로 연동해 줄 수 있는가.
- 문자·수어 상담이 처리할 수 있는 업무 범위와 동등한 조건을 유지할 운영 권한이 있는가.
- 콘텐츠 제작자가 공통 원본을 유지할 수 있는가. 정정 동기화가 추가 작업을 줄이는가, 늘리는가.
- 이용 방식 카드를 전달하는 것이 그때마다 직접 설정·설명하는 것보다 편한가.
- 구매 담당자가 접근성 검수 결과를 인수·갱신 결정에 반영할 수 있는가.
- 기관이 당사자 참여 보수와 재시험을 포함한 비용을 실제로 지불할 의사가 있는가.
